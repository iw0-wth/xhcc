# Streaming frontend: implemented file path and remaining work

Status: the default **XHCC file compilation path now uses source-pull -> bounded preprocessor sink -> filesystem spool -> window-backed lexer**. Main files and included files no longer need to fit a complete source buffer, and expanded text is written incrementally rather than accumulated in a complete RAM output buffer. The non-XHCC compatibility path still reads complete source/preprocessed buffers. This is a bounded frontend text-transport claim, not a fixed-memory claim for the entire compiler.

Production tests have passed, including >1MiB main/include tails executed on ARM and RV32 and >1MiB preprocessing output. Standalone reader/preprocessor/lexer and diagnostic checks, the complete unified integration suite and four-application SD/resource gates also passed. Compatibility regressions involving long whitespace and raw asm `#` immediates were fixed while retaining old `-E` byte comparisons and relocation-test expectations. A later arena-OOM check exposed a spool leak on explicit process exit; cleanup registration has now been added, and the complete regression rerun after that change passed, including explicit-exit and arena-OOM temporary-file assertions. Earlier passes do not establish cleanup for every failure mode. This establishes the tested text-transport path, not a completed MicroPython build.

## Storage, publication and memory boundaries

The implemented transport preprocesses to a spool before lexing. It genuinely bounds source/output text buffers in RAM, but it requires auxiliary writable storage. On host/WASI, the backend uses the mounted filesystem. For MCU deployments this storage must be provided by the SD/filesystem adapter; the current host/WASI implementation and emulator tests do not establish execution on MCU hardware. An all-RAM or read-only Flash-only compile path is not implemented.

[Spool creation](../src/platform/wasi/flash_fs_host.c#L171) uses an exclusive temporary beside a named -E output so successful publication can replace that output atomically. Other compilations use `XHCC_TMPDIR` when set, otherwise the current directory. A deployment should configure this directory to writable SD/temporary storage and budget for the expanded TU, including macro expansion. Do not silently place repeated spool writes on SPI Flash; its wear policy is a deployment decision. File names are collision-checked, and cleanup targets only temporaries the compiler owns. Normal return and successful publication/destroy release the corresponding registry entries. The new registry keeps heap-owned path/stream nodes and registers `atexit` cleanup so explicit `exit` paths, including arena OOM, can attempt to close/remove active spools without referencing expired frontend stack frames. Registry memory grows with active spools and actual path lengths; it is separate from the allocation-free source reader. Cleanup is best effort: `_Exit`, a runtime trap, forced termination or power loss can bypass it, and close/remove operations can fail. Do not claim all failure paths are leak-free; the full regression after the OOM fix passed with explicit-exit and arena-exhaustion cleanup checks. Existing destination data remains intact when preprocessing or spool publication fails. Streaming -E to stdout cannot roll back bytes already written if a later stdout write fails.

Limits are explicit and separate from total input length:

- Raw reader window: default 1024 bytes, configurable 1..4096 bytes.
- Preprocessor: 1024-byte raw window and 8192-byte logical-unit scratch per configured source frame; a token/directive/macro invocation longer than 8190 bytes is rejected. Frame count, include depth, macro storage and expansion limits remain configured resources.
- Preprocessor sink: 1024 bytes before flushing to the spool.
- Lexer token: 4096 bytes; copied asm body/source span: 65536 bytes.
- Input and spool offset/size: <= INT_MAX. `fs_file_size` rejects negative `ftell` results and positive long64 values above INT_MAX before casting.

AST, stable token spellings, macro tables, IR, optimization and generated code storage still grow with program complexity and remain subject to their own pools/budgets. A >1MiB file dominated by comments can compile with a small AST; that does not prove a >1MiB file containing arbitrary amounts of declarations can fit the same memory. libc FILE buffering and runtime memory are additional to the source-window measurements.

## Validation recorded so far

The following checks passed against the production XHCC file path; the complete compatibility suite and SD/resource gates also passed after the language regression fixes. Those recorded passes precede the subsequent explicit-exit/OOM cleanup fix; its complete rerun remains pending confirmation:

- [Production stream tests](../tests/test_stream_compile.py): four test methods covering real large-file compilation, output and spool storage. Main input and included header each exceed 1MiB; trailing declarations survive, and mixed archive linking/execution yields 73 on ARM and RV32. This establishes tail behavior beyond the old input/include caps, not merely successful reader access.
- The same suite verifies >1MiB -E output, byte equality between named output and stdout, forced includes/dependencies and several window-edge fixtures. Embedded NUL, explicit #error and oversized preprocessing units fail while preserving the previous named output; owned spool temporaries are cleaned up.
- Spool fault tests cover exclusive-name collisions, short writes, write/flush/close/rename failures, range reads and publication. These verify the implemented storage API, not power-loss durability.
- [Standalone preprocessor](../tests/test_stream_preproc.py) and [standalone lexer](../tests/test_stream_lexer.py) checks have passed; integrating-owner diagnostic checks passed across four application configurations. Full old-frontend compatibility results must be reported separately after regression fixes freeze.

The original [reader tests](../tests/test_source_reader.py) independently compile only their harness, the reader and real filesystem backend for native and WASI. Both passed with no skips. A 1,049,607-byte fixture is consumed completely with interleaved random absolute lookups. Counted real range I/O makes 1026 calls with maximum request 1024. Direct `malloc/calloc/realloc` references are poisoned during linkage. Fake callbacks exercise positive short reads, early-zero truncation, negative failures and return values larger than requested. One/two-byte windows split CRLF and UTF-8; NUL, EOF, cached checkpoint restoration/eviction and virtual INT_MAX tail access are covered.

Reader-owned payload peak is 1024 bytes; WASI metadata is 56 bytes (1080 total including window), native 64-bit metadata is 72 bytes (1096 total). These are primitive measurements, not the combined production preprocessor/lexer footprint. Run `python tests/test_source_reader.py` for that isolated evidence; Windows SDK runtime DLL directories may need to be on PATH (on the current machine `D:/miniconda3/Library/bin`).

## Remaining work and regression acceptance

The first real >32KiB path and >1MiB input/output tail tests are implemented. The immediate remaining task is to finish compatibility regression and fix any discovered differences without reintroducing whole-source buffers. After final source freeze, build/test all four applications and report full-suite evidence separately from the targeted results above.

Further work remains explicit:

1. A resumable preprocessor producer feeding a small lexer ring would remove the complete disk spool and its write/storage requirement. It is not implemented. Expansion/include cursors and bounded pending argument/token state would need to survive every producer suspension.
2. Persist precise raw physical file/offset/line and macro expansion origins, using the existing optional emission-map interface or another bounded/disk-backed representation. Production currently does not capture that mapping. Later source echo uses expanded spool locations; do not describe this as complete original-source macro/include provenance.
3. Improve diagnostic lookup I/O with bounded checkpoints or stored offsets while preserving memory bounds and correct clipped caret placement. Do not add an unbounded RAM line index.
4. Add/refine boundary coverage for all token/comment/escape/trigraph/splice placements, very long lines, macro arguments, nested includes, explicit limit errors and cross-window asm. Run the historical language/diagnostic suites; targeted large comments and tails do not cover every preprocessing semantic case.
5. Validate the SD/filesystem spool adapter and failure cleanup on actual MCU hardware, document writable-volume/free-space/wear policy, and measure the combined production frames, scratch, lexer, diagnostic, AST/IR and runtime footprint. A host/WASI pass is not hardware evidence.

## Actual project acceptance: MicroPython through its Makefiles

The final objective is building a large repository such as MicroPython by reading its original Makefiles. Large-TU streaming is a prerequisite, not project-level completion. Acceptance must load and evaluate the real build graph, preserve the required variable expansion phases and included Makefiles, run generated-header prerequisites before dependent compilation, compile multiple translation units with the selected port/configuration flags, and produce the expected linked result. A script with a hand-written source list does not substitute for the original Makefile build. The current internal make subset cannot yet execute MicroPython's complete original Makefile chain; the separate read-only build-chain audit must identify the supported target/port and remaining make, generator, compiler and linker gaps before claiming that milestone.

Validation must include a clean build, repeat build with no unnecessary work, edits to source/configuration/generated-header inputs with correct dependency invalidation, and incremental relinking of the affected objects. A failing TU must report its own file/location and release its source windows, diagnostic provider, spool and per-TU state; subsequent TUs or a retry must retain correct diagnostics and recover the intended resources. Cross-TU configuration, macro state and dependency tracking must not leak between units.

Host-side Python generation is permitted by the user and should be represented honestly as a host build prerequisite where the original project requires it. That permission does not add Python or other host-generator dependencies to target runtime execution. Report generation and target execution as distinct stages with their actual tools and artifacts.

Report resource evidence separately for per-TU input/output windows and scratch, build-graph/variable/dependency storage, macro tables, AST/IR pools, linking, and temporary disk. A bounded source reader does not bound the Makefile graph, macro expansion or AST/IR; a successful small-AST large comment fixture does not demonstrate a complete MicroPython build within the target budget. Keep the project-level acceptance open until the original build chain and required target execution are verified.

## Reader primitive contract

[Public reader interface](../include/xh_source_reader.h) and [implementation](../src/frontend/c/source_reader.c) remain allocation-free and expose no read-all operation. `xh_source_init` takes a callback `(context, absolute_offset, buffer, count)`, declared size <= INT_MAX and a caller-owned window. Persistent FILE, Flash and WASI callbacks can own handles through context; the reader does not free or close borrowed resources.

`xh_source_open` borrows its path until close and uses `fs_file_size`/`fs_read_range`. Its callback context points to the reader itself, so a live file reader cannot be copied/moved. The current range adapter reopens on each refill; persistent handles are an optional performance improvement.

Absolute `read_byte` can evict the cache but does not alter consumption offset/line/column. Relative `peek` requires lookahead < capacity. `consume` counts split CRLF as one newline, lone CR/LF as newlines, and columns as bytes rather than Unicode display cells. NUL is data at this layer; the preprocessing frontend rejects it explicitly. A trusted mark restores location only while its offset remains in the current cached window, or at the same current EOF cursor. Random access can evict that history.

Positive short reads are retried; zero before declared EOF, negative results and oversized callback counts become sticky I/O errors. Failed consume does not change its output byte or cursor state. Files must remain immutable during reader lifetime. Random lookup bounds resident memory but may perform arbitrarily much I/O. The integrated [filesystem size guard](../src/platform/wasi/flash_fs_host.c#L100) prevents long64 positive overflow before the int cast; long32 unrepresentable `ftell` results use the existing negative-result failure path.
