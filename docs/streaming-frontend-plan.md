# Streaming frontend migration: bounded reader foundation and immediate next phase

Status: reader primitive implemented and independently tested; **the compiler frontend still loads complete source and complete preprocessed output**. Adding this unused source to a build, or observing linker garbage collection, does not establish streaming compilation. Next priority is the actual preprocessor/lexer source-pull migration, not additional reader-only infrastructure.

## Delivered primitive and contract

[Public interface](../include/xh_source_reader.h) and [implementation](../src/frontend/c/source_reader.c) provide no allocation and no read-all API. Caller supplies 1..4096 bytes (recommended 1024). The reader retains only that window and constant-size metadata. `xh_source_init` accepts a reusable callback `(context, absolute_offset, buffer, count)` and declared file size <= INT_MAX. Future persistent FILE, Flash and WASI handle implementations own their handles through context; the generic reader neither closes nor frees borrowed resources.

`xh_source_open(path, window, capacity, reader)` borrows the path until close and uses `fs_file_size` plus `fs_read_range`. Its context points to the reader itself, so a live file reader must not be copied/moved. No global path storage exists. Each refill currently reopens the file through the range API; this is a correctness-first adapter with measurable reopen overhead. A persistent-handle callback can replace it without changing consumers.

- `read_byte(absolute)` permits random access with bounded resident memory, potentially unbounded total I/O. It may evict the window but never changes the consumption offset/line/column.
- `peek(relative)` requires relative < capacity and does not consume. It can cross a window boundary, so consumers must not retain pointers into the window.
- `consume` advances one byte and counts CRLF as one newline, including split CR/LF; lone CR/LF also count as newlines. Column is a byte column, not a Unicode display width.
- `mark`/`restore` use a trusted checkpoint containing offset/line/column/previous-CR. Restore is permitted only while the checkpoint is still within the current window, or is the same current EOF cursor. Random lookup can evict that history. This is not arbitrary backward seek with implicit line rescanning.
- Positive short reads are retried until the requested window or declared EOF. A zero read before declared size, a negative result, or result > request becomes sticky IO. Subsequent calls do not silently retry the damaged backend. Out bytes and consumption state are unchanged on failed consume. Files must remain immutable during reader lifetime.
- NUL is ordinary data. EOF is a separate result. The frontend must reject embedded NUL explicitly with a location, rather than interpreting it as EOF.
- Offset arithmetic never exceeds declared size <= INT_MAX. The file adapter depends on the filesystem size contract. The integration owner has added the explicit `sz > INT_MAX` / `EOVERFLOW` guard in [fs_file_size](../src/platform/wasi/flash_fs_host.c#L100) before casting its long result to int. On long32 hosts, an unrepresentable `ftell` result is rejected by the existing negative-result branch; on long64 hosts the explicit guard prevents a positive oversized result from wrapping during the cast. This filesystem correction is integrated alongside the reader foundation; it does not migrate frontend consumers.

## Immediate next phase: first real >32KiB compile

Implement one end-to-end path in the next owner-controlled change: main file and includes source-pull -> incremental translation/directives/macros -> bounded emitted stream -> lexer -> parser. Do not first collect source into a new growable allocation or increase the cap. A bounded directive/token/argument resource cap is acceptable when diagnosed explicitly; total source size must be independent of those caps.

Two output transport choices are valid; choose and ship one in that next change:

1. A resumable preprocessor producer feeding a small output ring. Lexer pulls only as needed. Expansion/include frames retain their cursors, with bounded expansion depth, pending token and argument scratch. This avoids auxiliary storage but requires conversion of the current recursive process loop into a state machine.
2. A chunked preprocessed spool on host/WASI filesystem or MCU SD, then a range-backed lexer reader over that spool. This bounds RAM and is a real streamed input/output frontend even though preprocessing finishes before lexing. It does not guarantee compilation without external writable storage. Keep the spool out of SPI Flash by default to avoid write wear; select SD/temporary-storage policy explicitly. Introduce internal temporary create/append/close/remove contracts rather than repeatedly calling `fs_write_file` (which replaces whole outputs). Names must be collision-safe, cleanup must run on success and all errors, and an incomplete spool must never become the user-visible -E output. Publishing -E still follows the established temporary-and-replace output policy. Document the required disk budget and failure diagnostics. The spool approach is likely the smallest first complete migration because the current parser may need historical asm spans.

Either approach must remove the entire preprocessed `out_buf`; replacing only input reads leaves the same total-size bottleneck. Preserve explicit origin spans (raw physical file/offset/line plus emitted offset); a whole-origin-text table or an unbounded line-index allocation would move the memory problem. For late diagnostics over spool, range-read the bounded excerpt at the stored offset. If a requested physical line exceeds excerpt capacity, show a clipped excerpt with correct caret policy. No silent wrong-source echo.

Include frames keep their own path storage alive (the reader borrows it), conditional-stack restore, include guards and dependency classification. Macro bodies intentionally have owned bounded storage; expansion frames can use a memory-fragment cursor distinct from the file reader. Function-like arguments, nested commas/parentheses, quotes/escapes and multiline comments need persistent scan state, not a one-line assumption. Preserve line directives/pragma forwarding and final-newline diagnostics.

## Acceptance gates for the next phase

- Compile an actual >1MiB C translation unit whose AST remains small (many comments/blank lines), and include a >1MiB header with meaningful trailing declarations/directives. Validate emitted code executes the tail declaration; a reader-only test is insufficient.
- Independently exceed the old preprocessed-output cap using many harmless emitted tokens/lines, while bounded AST pressure stays controlled. Compare -E byte-for-byte against the old implementation for small fixtures and an external reference where semantics match.
- Put comment delimiters, escapes, quotes, token paste/stringification, identifiers/numbers, UTF-8, CRLF, trigraphs and backslash-newline on every relevant window edge. Test final token without final newline, explicit NUL rejection, include-depth overflow and bounded token/argument overflow.
- Ensure diagnostic echo/caret correctness after refill, include pop, macro expansion, #line/pragma updates and EOF; asm bodies spanning windows must remain valid.
- Inject source/spool short-read, early EOF, read/write/close failures; prove failed outputs are not published and temporary resources are removed. Report reader windows, scratch, include stack and metadata separately from AST/IR pools and runtime stdio buffering.
- Run all four application builds and relevant compiler suites only after frontend owners freeze their edits; unused reader garbage collection is not an acceptance claim.

## Foundation test evidence

[Independent test](../tests/test_source_reader.py) compiles only its harness, the new reader, and the real filesystem backend, not the compiler app. It runs native and WASI targets. `malloc`, `calloc` and `realloc` are redirected to undefined poison symbols, so an accidental direct allocation fails linkage. The fixture is 1,049,607 bytes, generated/written in chunks. The harness consumes all bytes and validates interleaved random absolute lookups without losing sequential location state.

Both standalone native and WASI tests passed (2 tests, no skips). WASI observed payload peak is 1024 bytes; reader metadata is 56 bytes (1080 bytes including caller window). The native 64-bit build reports 72 bytes metadata (1096 total). This describes reader-owned storage, excluding libc FILE buffers, runtime memory and the test process. A counted real range callback makes 1026 calls with maximum request 1024, proving the complete >1MiB scan uses window-size range requests. Fake callbacks verify positive short-read completion, early-zero truncation, negative failure and oversized result rejection. The INT_MAX boundary uses a virtual callback so no 2GiB fixture is needed. One/two-byte windows exercise split UTF-8 and CRLF, NUL data, empty/normal EOF, bounded lookahead and checkpoint eviction/restore.

Run: `python tests/test_source_reader.py`. Windows SDK runtime DLL directories may need to be on PATH (on the current machine `D:/miniconda3/Library/bin`); the first attempted SDK invocation lacked that directory and exited 0xC0000135 before compilation, then passed with the existing DLL path configured. No main build artifact is changed by this test.
